2. Recommended URL contract

Keep existing curated URLs for continuity. Add two physical, prerendered HTML shells which hydrate their selected archive in the browser. Two shells are still constant-cost and clearer than one overloaded route; both can reuse the same detail component.

Explicit policy, not inferred UI

Introduce an explicit configuration allowlist, e.g. taxonomy.highlighted_tags: [automation, java, programming]. Keep topics as presentation data. Do not infer indexability from homepage cards, popularity, or the presence of an optional title. Validate each configured term exists, has visible content, and has adequate curated copy. Start with no highlighted categories; add a separate category allowlist only if that is an intended feature.

Generate one effective taxonomy policy consumed by route generation, sitemap, layout robots, URL helpers, and tests. For the dynamic curated route, use bounded entries with prerender = 'auto' if keeping non-prerendered compatibility handling in the same route. Keep crawl: false; do not allow wildcard fallback entries to silently restore all-tag generation.

The shell itself should be prerendered, not just served through 404.html. It must not read request-specific search parameters during prerender. Render a deterministic loading/selection shell with noindex in initial HTML, then react to the selected term in the browser. Do not set global ssr = false: that would damage all existing indexable pages.

3. SEO contract and hazards

  • Initial HTML is authoritative: curated topics contain one index, follow robots tag; both shared shells contain one noindex, follow tag before JavaScript runs. Do not start every route with noindex and attempt to turn curated routes indexable after hydration.
  • Fix the root layout classifier: the existing generic single-segment rule would consider new /tag/ and /category/ shells indexable. Exclude them before that rule. Replace the blanket /tag/* exception with exact allowlist membership.
  • Do not block the shell in robots.txt: crawlers must fetch it to observe noindex. Current Disallow: /category/ conflicts with this. Handle existing blocks for the directories consistently. Robots disallow alone is not a guarantee that a known URL disappears from search.
  • Curated rendering requires crawlable resources: current Disallow: /metadata/ must be reviewed if crawler rendering needs config or JSON. Either prerender/serialize all required curated data or allow necessary resources. Non-indexed shells do not need crawler-rendered content to convey noindex.
  • Sitemap: only exact highlighted archive paths; never shell query variants or uncurated legacy paths. Prerender manifest includes curated archives plus the two shells and other intentional static pages. Prerenderable and indexable are separate concepts.
  • Canonical: retain self-canonical curated URLs. A query-detail shell may omit canonical while remaining noindex; recommended for this design, rather than declaring unrelated terms equivalent. If retaining self-canonicals, include the selected term and strip only view parameters. Current pathname-only canonical generation loses all query selection. A query URL for a highlighted tag should navigate to its static URL, not remain a duplicate archive.
  • Metadata: keep curated CollectionPage/ItemList structured data, title, intro, description, and article links in static HTML. Generic shell title before hydration; selected term/title after hydration. Shells do not need SEO collection schema. Keep one owner for robots and canonical to avoid conflicting tags.
  • Search visibility: non-curated tag landing pages intentionally lose organic landing opportunities. Preserve article/portfolio indexability, feeds, and curated internal links; do not add blanket nofollow to taxonomy chips. Noindex pages should not become the only discovery path to articles.
  • Social previews: query variants share generic shell preview metadata because many unfurlers do not execute JavaScript. Curated topics retain meaningful previews. Tail-specific unfurls would require server/edge rendering or dedicated HTML, which is outside this static-shell design.

References: Google: noindex requires crawler visibility · Google: JavaScript rendering, blocked resources, and soft-404 handling.

URL correctness

Use encodeURIComponent for path segments and URLSearchParams for query values. Preserve exact term identity; current filtering uses case-sensitive equality, while topic presentation falls back to lowercase. Do not silently merge Java and java. Test Unicode, spaces, +, &, #, %, slash-containing terms, and double-encoding. Unsupported path terms should be rejected or assigned stable safe IDs. Treat names as data, never unescaped HTML or unchecked filenames.

5. Build savings are real; runtime scaling still needs work

With T tags, H highlighted tags, and N content records, current per-tag scanning has roughly O(T × N) work and repeatedly serialized data. The hybrid design bounds tag HTML count at H + 1; the category shell adds one more fixed page. Metadata generation still processes all content and associations. Article rendering, image variants, search indexes, and content copying do not become cheaper automatically.

Minimal change

Reuse existing full-array loaders in shared shells. Lowest implementation risk, suitable for today's small dataset. A tag view fetches about 157 KB of local JSON before HTTP compression, plus config and JavaScript. At scale, this still downloads and scans everything.

Growth-ready recommendation

Generate compact per-term result data with IDs, counts, and paginated summaries; fetch only the selected term/page. Curated prerender uses the same results. A small registry maps exact names to safe IDs, avoiding raw user input in file paths.

Tradeoff

Term JSON shards still add files and metadata work proportional to associations, but avoid duplicating the whole application shell and unrelated content in each HTML page. Bucket data if file-count limits become material. Pagination must bound transfer as well as rendered DOM.

  • Current tag loader swallows failures into empty arrays. The new view must distinguish loading, request failure with retry, unknown term, and known term with zero matches. Never disguise a network error as an empty archive.
  • Use cancellable requests or latest-request protection when the query changes; support back/forward navigation, reloads, and modified-link/new-tab behavior. Avoid one-time onMount parsing that leaves the view stale on client navigation.
  • Provide accessible loading/status announcements, stable layout, focus handling and genuine anchor links. A no-JavaScript visitor should see an explanation and links to the main listings/curated topics rather than an infinite skeleton.
  • Current term counts are collected across content sections, while tag detail excludes pages/docs and category detail additionally excludes thoughts. Define the visible scope explicitly so chips/counts match results; preserve mixed content intentionally.
  • Reuse date ordering consistently and bound detail-page DOM for popular topics. Preserve the existing bounded taxonomy-directory pagination rather than replacing it with accumulating load-more.
  • Version result metadata consistently with the existing Vite build token. Prerendered pages, hydrated config and downloaded shards must agree across deployments; test a tab left open during rollout and cached stale assets.

6. Migration and hosting decision

The critical hosting constraint: GitHub Pages' 404.html fallback can make client navigation appear functional, while a fresh request to a removed archive still returns HTTP 404. New query URLs avoid this because /tag/index.html and /category/index.html really exist. Old bookmarks/backlinks need an explicit migration strategy.
Preferred when HTTP redirect control exists

Use a real permanent redirect from each valid old non-curated archive to its exact query URL; exclude highlighted paths. Confirm deployed behavior, not merely a file named _redirects, which GitHub Pages does not process. Avoid decoding/encoding twice, redirect loops, and arbitrary redirect targets. Unknown terms should remain genuine not-found cases.

Pure GitHub Pages alternative

Retain client compatibility routes as best-effort user navigation, understanding initial 404 and generic previews remain. Temporary static noindex redirect stubs can keep old URLs fetchable and let crawlers see deindexing, but retain O(T) files during the transition and are not HTTP 301 redirects. Choose a sunset period only after considering existing search traffic and backlinks.

Suggested rollout order: explicitly configure the three highlights and shared policy; add noindex shells and reusable views; switch every generated chip and relevant authored link; restrict manifest/sitemap and update robots atomically; publish verified legacy migration; monitor search, client failures, build time and artifact size. Promotion preserves the old curated-style path and makes helper links static; demotion needs the same legacy redirect/deindexing treatment as initial rollout. Clean deployments prevent old indexable HTML from lingering. Rollback must restore policy, routing, sitemap and robots together.

No need to introduce SSR infrastructure just to accomplish this. Redirect infrastructure is a separate decision. A strict single-shell preference could use /taxonomy/?kind=tag&name=cucumber, but it adds a new namespace and kind validation with negligible savings versus two shared shells.

7. Acceptance and verification

  • Generated artifacts: exactly the configured highlighted tag details appear in sitemap and generated archive HTML. Both shell files exist; no extra tag/category HTML remains after a clean build, except explicitly time-limited migration stubs.
  • Raw HTML: curated topics return complete content, correct canonical, useful description, collection schema and exactly one index robots tag. Shells return exactly one noindex robots tag even with JavaScript disabled.
  • Deployed HTTP: new query URLs return 200 on direct requests/reloads; curated paths return 200; migrated legacy paths return the chosen documented status/redirect. Preview servers may hide GitHub Pages fallback differences.
  • Navigation matrix: post/portfolio/thought/directory links, Markdown links, mixed-content results, browser back/forward, new tabs, query changes, encoded names, invalid/missing/duplicate parameters, promoted/demoted topics, and unknown terms.
  • Failure matrix: interrupted requests, missing JSON, no connection, stale build/config, rapid term switching, retries, no JS and no browser runtime errors.
  • SEO regression: article/portfolio routes and feeds unchanged; shells excluded from sitemap and not robots-blocked; no duplicate canonical/robots tags. Sitelinks and llms configuration still validate.
  • Scale: test thousands of terms and a high-volume term; compare clean build duration, output size, HTML count, cold detail transfer, parsing time and DOM count. Do not extrapolate a measured speedup from file-size reduction alone.
